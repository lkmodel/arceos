# `batch mode`

## 加载模块原理

为了方便讨论，我们分别称呼内核部分与其在内存中的分布为 `Kernel`，
应用部分与其在内存中的分布为 `App` ，同理，库部分为 `Lib`。

在运行时，会优先加载 `Kernel`，并初始化 `ABI CALL TABLE`、伪进程管理。
参考 `batch_apps`下文件，解析文件头部数据与执行脚本数据。
对头部文件进行判断，当 `Lib` 有效（大小不为0）时，进行加载 `Lib`，
并进行动态链接，但是空出来由 `start_c` 调用的 `App` 的入口函数。
根据执行脚本与头部数据配合，获得对应应用的 `App ELF`，根据其类型，
进行动态加载或静态加载。

当启动一个动态 `App` 时，将会从 `Lib entry` 进入执行，由 `Lib` 调用到 `App`，
当启动一个静态 `App` 时，将会从 `App entry` 进入执行。
静态 `App` 在加载时要求使用 `mocklibc` 静态库，其中的入口函数与 `Lib` 库是一致的，
所以调用的函数流是一致的，只是由不同部分（`LIb`、`App`）进行调用。

## 加载模块注意点

`Lib` 库内的全局变量比较少，在应用退出后没有进行任何处理，新的应用的开发不应当假定任何初始值，
对环境的协同操作应当通过传递参数的形式进行。

不建议在存在动态库的情况下依然加载执行静态链接，
我们建议可以在纯粹静态链接的情况下去使用（没有加载动态库）。

在加载 `Lib` 库的时候，会进行判断是否大小为0。如果大小为0，则认为没有加载 `Lib`。
