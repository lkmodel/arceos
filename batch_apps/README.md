# 批处理模式构建脚本说明

## 1. 概述

本文档描述了一个用于将多个应用程序、可选的共享库 (`Lib`) 以及执行指令打包成单一二进制文件 (`apps.bin`) 的批处理构建脚本及其规范。
该工具旨在简化应用在特定目标环境（ ArceOS）中的聚合与部署。

## 2. 核心规范

### 2.1. 应用包类型定义

为了清晰地管理依赖和包内容，我们根据 `Lib` 库的存在与否及包内应用类型定义了以下应用包类型：

**判断 `Lib` 库是否存在:**

* **不存在 `Lib` 库**: 当 `Lib` 库的大小为 `0` **并且** 其起始地址也为 `0` 时，认定包不含 `Lib` 库。
* **存在 `Lib` 库**: 当 `Lib` 库的大小**不为** `0` **并且** 其起始地址也**不为** `0` 时，认定包包含 `Lib` 库。

**包类型分类:**

* **纯静态应用包 (Pure Static Application Package)**
  * **条件**: **不存在** `Lib` 库。
  * **内容**: 包内**仅包含**静态应用，不允许包含任何动态应用。
* **混合动态应用包 (Mixed Dynamic Application Package)**
  * **条件**: **存在** `Lib` 库。
  * **内容**: 包内**同时包含**动态应用和静态应用。
* **动态应用包 (Dynamic Application Package)**
  * **条件**: **存在** `Lib` 库。
  * **内容**: 包内**仅包含**动态应用。

**未定义情况:**

* 任何不满足上述 `Lib` 库存在/不存在判断条件的情况（如大小为 `0` 但地址非 `0`，反之亦然）均视为**未定义**。
* 任何包的内容组合不符合上述三种类型定义的，也视为**未定义**。

### 2.2. 应用包 (`apps.bin`) 文件结构

生成的 `apps.bin` 文件由**头部元数据**和**实际数据**组成：

**头部元数据:**

| 字段               | 大小 (字节) | 说明                                        |
| :----------------- | :---------- | :------------------------------------------ |
| 魔数 (Magic)       | 8           | 文件标识符                                  |
| 应用总数 (Count)   | 4           | 包内包含的应用数量                          |
| 头部大小 (HdrSize) | 8           | 整个头部区域的总字节数                      |
| **[应用信息块]** |             | *重复 '应用总数' 次* |
| > 应用N - 大小     | 8           | 第 N 个应用的文件大小                       |
| > 应用N - 名字     | 可变        | 第 N 个应用的文件名 (以 `\0` 结尾的字符串) |
| > 应用N - 起始地址 | 8           | 第 N 个应用数据在文件中的偏移量             |
| **Lib 库信息** |             |                                             |
| > Lib - 大小       | 8           | `Lib` 库文件大小 (若无则为 0)               |
| > Lib - 起始地址   | 8           | `Lib` 库数据在文件中的偏移量 (若无则为 0)   |
| **脚本信息** |             |                                             |
| > 脚本 - 大小      | 8           | 编码后执行脚本的大小                        |
| > 脚本 - 起始地址  | 8           | 编码后执行脚本数据在文件中的偏移量          |

**实际数据:** (紧随头部之后，按头部中指定的起始地址排列)

1. 应用 1 的文件数据
2. 应用 2 的文件数据
3. ...
4. `Lib` 库数据 (如果存在)
5. 编码后的执行脚本数据
6. 填充字节 (Padding zeros to 32MB total size)

### 2.3. 执行脚本格式 (编码后)

执行脚本 (`script.txt`) 被编码成二进制格式存储，结构如下：

| 字段                     | 大小 (字节) | 说明                                              |
| :----------------------- | :---------- | :------------------------------------------------ |
| 魔数 (Magic)             | 8           | 脚本文件标识符                                    |
| 指令行数 (Lines)         | 4           | 有效指令的数量                                    |
| **[指令行数据]** |             | *重复 '指令行数' 次* |
| > 行头部验证 (0xFF)      | 1           | 固定字节，用于校验或同步                          |
| > 参数个数 (argc)        | 4           | 当前行命令的参数数量 (含应用名)                   |
| > 应用名称 (argv[0])     | 可变        | 应用名 (以 `\0` 结尾, **不含路径**)               |
| > 参数 1 (argv[1])       | 可变        | 第一个参数 (以 `\0` 结尾, 如果 `argc > 1`)       |
| > ...                    | ...         | ...                                               |
| > 参数 N (argv[argc-1])  | 可变        | 最后一个参数 (以 `\0` 结尾, 如果 `argc > 1`)     |

**`argv` 处理注意:**
与标准 C 的 `main` 函数参数不同：

* `argv[0]` 仅为应用名，不包含路径。这是为了简化脚本编写。
* 虽然 `argc` 计数正确，但系统（ ArceOS）的加载器**预期不会**访问 `argv[argc]`，因此脚本编码不保证其为 `NULL`。

## 3. 编写与使用规范

### 3.1. 执行脚本 (`script.txt`) 编写规范

* 在项目根目录创建 `script.txt` 文件（或由 `Makefile` 中 `SCRIPT` 变量指定）。
* 采用**类 `Linux` 命令**风格，每行一个命令，用于启动一个应用。
* **第一个词**必须是**应用名称**，且该名称必须与 `APPS` 目录下的某个文件名**完全一致**。
* 应用名称后，使用**空格**分隔传递给应用的参数。
* 允许空行，空行将被忽略。
* 示例:

    ```txt
    app1 param1 param2
    app_without_suffix arg_a
    app3
    ```

### 3.2. `APPS` 目录规范

* 该目录（路径由 `Makefile` 中 `APP_DIR` 变量指定，默认为 `APPS`）用于存放**所有**需要打包的应用程序**可执行文件**。
* **严格要求**:
    1. 目录下的**文件名**必须与 `script.txt` 中使用的应用名**完全一致**。不建议使用 `.bin` 等后缀，若使用，则脚本中也必须包含。
    2. 目录下**不能**存放任何**非可执行文件**（如源代码、文档、子目录等）。这是因为打包脚本会直接将此目录所有文件视为应用打包，且加载器依赖文件名匹配。

## 4. 构建与运行

### 4.1. 构建配置 (Makefile 变量)

可在 `Makefile` 文件顶部修改以下主要配置变量：

* `APP_DIR ?= APPS`: 应用程序可执行文件所在的目录。
* `INCLUDE_LIB ?= 1`: 是否包含 `Lib` 库。
  * `1` (默认): 包含。**当 `APPS` 中有动态应用依赖 `Lib` 时必须设为 `1`**。
  * `0`: 不包含。用于纯静态应用包。
* `MOCK_LIBC_SO ?= ../ulib/mocklibc_lib/lib/libmock.so`: 指定 `Lib` 库文件的路径 (仅当 `INCLUDE_LIB=1` 时生效)。
* `SCRIPT ?= script.txt`: 指定执行脚本文件的名称。

### 4.2. 执行构建

1. **准备 `APPS` 目录**: 按 `3.2` 规范放置好应用可执行文件。
2. **编写 `script.txt`**: 按 `3.1` 规范编写执行脚本。
3. **确保 `Lib` 库存在**: 如果 `INCLUDE_LIB=1`，请确认 `MOCK_LIBC_SO` 指向的路径有效。
4. **运行 Make**: 在 `Makefile` 所在目录下执行：

    ```bash
    make
    ```

5. **获取结果**: 构建成功后，最终的 `apps.bin` 文件（大小为 32MB）会生成在 `build/` 目录，并同时复制一份到 `../payload/` 目录。

### 4.3. 清理构建产物

执行以下命令可删除 `build/` 目录及其所有内容：

```bash
make clean
```

# 批处理模式构建脚本

## 用户规范

### 应用包类型规范

为了清晰地定义不同类型的应用包，我们根据 `Lib` 库的存在与否以及包含的应用类型（静态或动态）进行分类。

#### 1. 如何判断 Lib 库是否存在？

不存在 `Lib` 库： 当 `Lib` 库的大小为 `0` 并且 其起始地址也为 `0` 时，我们认定该包不包含 `Lib` 库。
存在 `Lib` 库： 当 `Lib` 库的大小不为 `0` 并且 其起始地址也不为 `0` 时，我们认定该包包含 `Lib` 库。

#### 2. 应用包类型定义

基于 `Lib` 库是否存在，我们将应用包分为以下三类：

* 纯静态应用包 (Pure Static Application Package)
  * 条件： 不存在 Lib 库 (如上所述)。
  * 内容： 包内仅包含静态应用，不允许包含任何动态应用。

* 混合动态应用包 (Mixed Dynamic Application Package)
  * 条件： 存在 Lib 库 (如上所述)。
  * 内容： 包内同时包含动态应用和静态应用。

* 动态应用包 (Dynamic Application Package)
  * 条件： 存在 Lib 库 (如上所述)。
  * 内容： 包内仅包含动态应用。

#### 3. 未定义情况

任何不完全满足上述 `Lib` 库存在或不存在条件的情况（例如：大小为 `0` 但地址不为 `0`，或大小不为 `0` 但地址为 `0`）均被视为未定义。
任何包的内容组合不符合上述三种明确定义的类型的情况，也视为未定义。

## 应用包组织方式

生成的 `apps.bin` 文件结构如下：

```txt
[头部数据]
|  魔数（8字节）
|  应用总数（4字节）
|  头部数据大小（8字节）
|  应用1的大小（8字节） | 应用1的名字（字符串） | 应用1的起始地址（8字节）
|  应用2的大小（8字节） | 应用2的名字（字符串） | 应用2的起始地址（8字节）
|  应用3的大小（8字节） | 应用3的名字（字符串） | 应用3的起始地址（8字节）
|  Lib库的大小（8字节） | Lib库的起始地址（8字节）
|  脚本的大小（8字节）  | 脚本的起始地址（8字节）

[实际数据]
|  应用1的文件数据
|  应用2的文件数据
|  应用3的文件数据
|  Lib库数据
|  执行脚本数据
```

执行脚本格式如下：

```txt
[头部数据]
|  魔数（8字节）
|  指令行数（4字节）
|  行头部验证字节0xFF（1字节）| argc（4字节） | 应用名称argv[0], 以\0结尾 | 应用参数argv[1]，以\0结尾 | ... | 应用参数argv[argc-1]，以\0结尾
|  行头部验证字节0xFF（1字节）| argc（4字节） | 应用名称argv[0], 以\0结尾 | 应用参数argv[1]，以\0结尾 | ... | 应用参数argv[argc-1]，以\0结尾
|  行头部验证字节0xFF（1字节）| argc（4字节） | 应用名称argv[0], 以\0结尾 | 应用参数argv[1]，以\0结尾 | ... | 应用参数argv[argc-1]，以\0结尾
...
```

在 `ANSI-C C89/C99` 中说明了 `argv[0]` 指向程序运行时的全路经名，
`argv[1]` 指向程序在命令中执行程序名后的第一个字符串，
`argv[2]` 指向执行程序名后的第二个字符串， `argv[argc]` 为 `NULL`。

但是在执行脚本中并不是如此，应用名称并不会包含全路经名
（因为我们不期望用户编写脚本时需要指定路经，除非是必须的）；
`argc` 是符合标准的，但是 `argv[argc]` 却不是 `NULL` ，
因为 `ArceOS` 加载程序并不会实际访问 `argv[argc]`，这是没有意义的。

## 执行脚本编写规范

采用 `Linux` 命令风格，每一行代表了一个执行命令，用于加载一个 `App` 并让 `OS` 执行。
第一个参数的名称需要在APPS目录下存在，否则会在加载的时候报错；
第一个参数后，通过空格分割，可以向可执行文件传递参数，每一个参数用空格分开；
可以存在空行。

## `APPS` 目录命名规范

由于 `ArceOS` 中需要获取应用的程序名，而这个程序名的生成与脚本相关。
脚本会将整个文件名都视作应用程序名。

在 `APPS` 目录中，我们要求文件名与程序名保持一致。
也就是说，我们不要求存在诸如 `*.bin` 的后缀，也不要求有任何命名规范；
自然，当其中有一个 `*.bin` 的程序时，我们也要求编写脚本时也使用 `*.bin` 作为程序名。

出于上述因素，我们不建议添加任何后缀。

同样，由于加载脚本的原因，我们要求 `APPS` 库下面不能有任何非可执行文件。

## 如何运行当前目录？

将需要执行的脚本移动到 `APPS` 中，在当前目录下编写脚本 `script.txt`，然后执行 `make`。
执行之后会产生一个 32M 大小的 `apps.bin`，并且被移动到 `../payload/`。
我们假设直接使用 `../ulib/mocklibc_lib/lib/libmock.so`作为使用的库，
在库修改后需要重编译与重打包。

可以通过指定 `Makefile` 中的参数，进行选择编译。具体如何操作可以去读 `Makefile` 源码。

通过指定 `INCLUDE_LIB`，可以选择是否添加动态库。
请注意，当应用中至少有一个动态应用时，也应当进行加载。
默认参数是加载动态库
